# gitlab-mcp 1.14.0 — auth rename, user-lifecycle ops, and LibreChat deployability

Status: Drafted 2026-04-27 (UTC). Awaiting review.

## Goals

1. Replace the three-way `GITLAB_AUTH_MODE` enum with two role-named env vars whose names encode the policy.
2. Add the missing user-lifecycle write tools (`delete_issue`, `delete_note`, `update_note`).
3. Make the server installable in LibreChat via the **Add MCP Server** UI by publishing a working container image and tightening the Dockerfile.
4. Rewrite the README around three concrete deployment shapes — solo Claude Code, LibreChat with read-only service token, LibreChat strict per-user — and lead each with the canonical install path for that platform.
5. Add a project logo and surface it via MCP `serverInfo` for nicer display in client UIs.
6. Document the HTTPS / reverse-proxy story for operators hosting this for a remote LibreChat.

This is a single coordinated 1.14.0 release. `GITLAB_AUTH_MODE` is removed in this release; no migration window.

## Non-goals

- `delete_merge_request` and `merge_merge_request` — defer to a follow-up.
- OAuth flows. We continue to use PATs.
- A hosted public instance of the server. We publish a container image; operators run their own.

## 1. Auth model rename

### Current (1.13.x)

Three env vars + a mode enum:

- `GITLAB_AUTH_MODE` ∈ `{shared, per-user, hybrid}` (default `hybrid`)
- `GITLAB_SHARED_ACCESS_TOKEN` — the "shared" token
- per-call `userCredentials` arg or `Authorization: Bearer …` header

In `hybrid` mode the shared token is allowed for reads but rejected for writes; in `shared` it does both; in `per-user` it does neither and per-call creds are required.

### Target (1.14.0)

Drop the mode enum. Two role-named env vars, mutually exclusive:

| Env var | Allowed for | Notes |
|---|---|---|
| `GITLAB_TOKEN` | Reads **and** writes | The token's scope (read_api vs api) is the operator's responsibility. |
| `GITLAB_READ_TOKEN` | Reads only | Writes against this token are rejected with a clear error. |

Resolution rule, applied per call:

1. If the call carries per-call user credentials (`userCredentials` arg in stdio, `Authorization: Bearer …` header in HTTP), use them. The user token can do reads and writes.
2. Else if the operation is a **read** and either `GITLAB_TOKEN` or `GITLAB_READ_TOKEN` is set, use it.
3. Else if the operation is a **write** and `GITLAB_TOKEN` is set, use it.
4. Else error: `Write operation requires a user token. Provide one via Authorization: Bearer (HTTP) or userCredentials (stdio), or configure GITLAB_TOKEN.`

`GITLAB_AUTH_MODE` and `GITLAB_SHARED_ACCESS_TOKEN`, if set, are ignored with a one-time deprecation warning logged at startup pointing at the new env vars. There is no aliasing — operators must update their config.

Setting both `GITLAB_TOKEN` and `GITLAB_READ_TOKEN` is a config error and the server fails fast on startup.

### Read vs write classification

The classification lives in the tool registry. Each tool entry gains a `write: boolean` field (default `false`). Tools that mutate GitLab state set `write: true`. The client uses this flag — surfaced through the call site — to decide whether step 2 or step 3 above applies. Tools currently under "Write Operations" in the README are the canonical write set; the new lifecycle tools (§2) join that set.

### Why this is better than the flag alternative

- The variable name encodes the policy. An operator who only intends to grant reads can't accidentally enable writes by misunderstanding a flag.
- Solo IDE setups drop one env var (no flag needed; just set `GITLAB_TOKEN`).
- The three deployment shapes map cleanly to "set `GITLAB_TOKEN`", "set `GITLAB_READ_TOKEN`", "set neither".

## 2. New user-lifecycle tools

Three tools, all write operations, all backed by GitLab GraphQL mutations:

| Tool | Mutation | Inputs | Returns |
|---|---|---|---|
| `delete_issue` | `destroyIssue` | `projectPath`, `iid` | `{ success: bool, errors: string[] }` |
| `delete_note` | `destroyNote` | `projectPath`, `noteableType` ("issue"\|"merge_request"), `iid`, `noteId` | `{ success: bool, errors: string[] }` |
| `update_note` | `updateNote` | `projectPath`, `noteableType`, `iid`, `noteId`, `body` | `{ note: { id, body, updatedAt } }` |

All three:

- Trim string inputs and reject empty required fields, matching existing tool conventions.
- Use the same `userConfig` plumbing as other writes — they receive the resolved per-call or `GITLAB_TOKEN` credentials and will reject if only `GITLAB_READ_TOKEN` is configured.
- Are added to `src/tools.ts` next to their related tools (`delete_issue` near `update_issue`, the note ops near `create_note`).
- Get matching client methods on `GitLabGraphQLClient` (e.g. `destroyIssue(projectPath, iid, userConfig)`).
- Are added to the README "Write Operations" table.

GitLab's `destroyIssue`, `destroyNote`, and `updateNote` mutations are stable on Free / Premium / Ultimate self-hosted and gitlab.com. We don't need a schema-introspection fallback.

## 3. Docker image publish + Dockerfile tighten

### Current state

`Dockerfile` is a build recipe that **self-clones the repo from GitHub** at build time. It's intended to be copied into a LibreChat checkout and built locally. The `release.yml` workflow doesn't build or push images — npm publish only. Healthcheck is fake (`console.log`). No `EXPOSE`. No registry image exists.

### Target

- Switch `Dockerfile` to a normal `COPY` from build context. Drop the `git clone` and `GITLAB_MCP_VERSION` build arg. The image is now built **from the repo**, not by it.
- Add `EXPOSE 8008` and set runtime defaults `MCP_TRANSPORT=http`, `GITLAB_MCP_PORT=8008`, `NODE_ENV=production`.
- Replace the bogus healthcheck with a real one against `/health`:
  ```dockerfile
  HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
    CMD wget -qO- http://localhost:8008/health || exit 1
  ```
  (Add `wget` to the runtime image — Alpine has busybox `wget` already, so no extra install.)
- Add a new GitHub Actions job (extend `release.yml` or add `docker.yml` triggered on the same `vX.Y.Z` tag) that builds for `linux/amd64,linux/arm64` and pushes:
  - `ghcr.io/ttpears/gitlab-mcp:1.14.0`
  - `ghcr.io/ttpears/gitlab-mcp:1.14`
  - `ghcr.io/ttpears/gitlab-mcp:latest`

  Authentication uses `GITHUB_TOKEN` with `packages: write`; no separate PAT required.
- Make the package public on GHCR so end users can pull without auth (one-time setting on the package after the first push).

### Smoke test for the image

`docker run --rm -p 8008:8008 ghcr.io/ttpears/gitlab-mcp:latest` should:

- Start cleanly with no `GITLAB_TOKEN` configured (per-user-only mode).
- Respond on `GET /health` with `{ status: "healthy", ... }`.
- Accept a streamable-HTTP MCP init at `POST /` with `Authorization: Bearer <PAT>` and return a valid session id.

### LibreChat (service-account reads) section

Single `librechat.yaml` example. Service token via env, per-user write PAT via `customUserVars`. Includes `startup: false` so the server doesn't error before the user supplies their PAT. The gitlab-mcp container has `GITLAB_READ_TOKEN` set (read-only fallback) and no `GITLAB_TOKEN`.

```yaml
mcpServers:
  gitlab:
    type: streamable-http
    url: http://gitlab-mcp:8008/
    startup: false
    headers:
      Authorization: "Bearer {{GITLAB_PAT}}"
    customUserVars:
      GITLAB_PAT:
        title: "GitLab Personal Access Token"
        description: "Your GitLab PAT with api scope. Used for issues/MRs/comments you create or edit."
```

### LibreChat (strict per-user) section

Lead with the **Add MCP Server** UI walkthrough — that's the path operators are most likely to want and it isn't documented today:

1. Host gitlab-mcp somewhere reachable from LibreChat (Docker run + reverse proxy, see "Hosting" section).
2. In LibreChat → MCP Servers → **Add MCP Server**.
3. URL: `https://your-host/`
4. Authentication: **API Key** → check **User provides key** → header format **Bearer**.
5. Save. Each user fills in their PAT via the MCP Tool Select Dialog.

Then show the equivalent `librechat.yaml` form for operators who prefer config-as-code.

### Configuration table

| Variable | Description | Default |
|---|---|---|
| `GITLAB_URL` | GitLab instance URL | `https://gitlab.com` |
| `GITLAB_TOKEN` | Full-access fallback token (reads + writes) | — |
| `GITLAB_READ_TOKEN` | Read-only fallback token (writes rejected) | — |
| `GITLAB_MAX_PAGE_SIZE` | Maximum items per page (1-100) | `50` |
| `GITLAB_TIMEOUT` | Request timeout in milliseconds | `30000` |
| `GITLAB_MCP_PORT` | HTTP server port | `8008` |
| `MCP_TRANSPORT` | Transport mode (`http` for LibreChat) | stdio |

Note explicitly that `GITLAB_TOKEN` and `GITLAB_READ_TOKEN` are mutually exclusive; setting both is a startup error. Note that `GITLAB_AUTH_MODE` and `GITLAB_SHARED_ACCESS_TOKEN` are removed in 1.14.0.

## 7. Hosting docs (reverse proxy / HTTPS)

A short subsection in the README — not implementation work, just guidance:

- The server speaks plain HTTP. For LibreChat-as-a-service or any cross-network deployment, put it behind TLS.
- Common patterns: Caddy (auto-TLS), Traefik (Docker-native), Cloudflare Tunnel (no public IP needed). One short docker-compose snippet showing Caddy in front of `gitlab-mcp` is enough.
- Note the `Authorization` and `Mcp-Session-Id` headers must pass through the proxy. (Most defaults handle this fine.)

No code changes for §7.

## Verification

This repo has no test infrastructure. Verification is a manual smoke checklist run after the build is green and before merging:

**Build & static checks**
- `npm run build` clean.
- `tsc --noEmit` clean (no implicit `any` from the removed `authMode` field).
- `docker build .` produces an image; `docker run` it locally.

**Stdio path (Claude Code-shaped)**
- Set `GITLAB_TOKEN` only → reads and writes succeed against the configured user.
- Set `GITLAB_READ_TOKEN` only → reads succeed, writes return the clear error from §1 step 4.
- Set both → server exits with the mutual-exclusion error.
- Set `GITLAB_AUTH_MODE=hybrid` and `GITLAB_SHARED_ACCESS_TOKEN=...` → server starts, logs deprecation warning, ignores both.

**HTTP path (LibreChat-shaped)**
- Container with no token + `Authorization: Bearer <user PAT>` → init session, call `get_current_user`, returns the user.
- Container with `GITLAB_READ_TOKEN` + no Authorization → reads work, writes return the clear error.
- Container with `GITLAB_READ_TOKEN` + `Authorization: Bearer <user PAT>` → writes work as the user, not the service account.

**New tools**
- `create_issue` → `update_note` (on a comment) → `delete_note` → `delete_issue` round-trip on a throwaway test project.

**Docker image publish**
- Tag pushed → `ghcr.io/ttpears/gitlab-mcp:1.14.0` exists and `docker pull` succeeds without auth.

**LibreChat "Add MCP Server" path**
- Stand up the published image behind a reverse proxy.
- In a test LibreChat instance: Add MCP Server → URL → API Key → User provides key → Bearer → save → user fills PAT → `get_current_user` returns that user.
